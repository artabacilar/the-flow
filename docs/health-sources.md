# Where the body numbers come from

The Sleep tab shows Recovery, Strain, Sleep performance, HRV and resting heart
rate. There are three ways they can get there, and the panel says which one it
is using rather than leaving you to guess.

| Source | Gives | Works on |
|---|---|---|
| WHOOP | Recovery, Strain, Sleep %, HRV, resting HR, hours asleep | everywhere you sign in |
| Apple Health | Sleep hours, HRV, resting HR, respiratory rate, workouts, steps | the iPhone app only |
| Typing it in | whatever you type | everywhere |

They are not redundant. Recovery and Strain are WHOOP's own scores, so only
WHOOP can answer those. Apple Health is where an Apple Watch, an Oura ring, a
Garmin and WHOOP's own app all deposit what they measure — so reading it covers
whatever you happen to be wearing, including whatever you switch to next.

Where both have a number for the same day, WHOOP wins and Health fills the
gaps. Neither ever overwrites a night you logged yourself: a number you typed
is a statement, and these are only measurements.

---

## What was here before

The panel used to ask `http://localhost:3000/whoop-data.json`. That address
means "this computer", so it could only ever answer on one laptop, with a
helper script running, and never on a phone. The permanent **"Helper not
running"** was not a broken helper. It was the architecture saying so out loud.

The server holds the connection now.

---

## Connecting WHOOP

This needs a WHOOP developer application, which only you can create — it is
registered to a person and agrees to WHOOP's API terms on their behalf.

**1 · Register the application**

At [developer.whoop.com](https://developer.whoop.com), create an app with:

- **Redirect URI** — `https://theflow.today/api/whoop/callback`
  Exactly this. WHOOP matches it character for character and refuses the token
  exchange if it differs, with an error that talks about the redirect rather
  than about the mismatch.
- **Scopes** — `offline`, `read:recovery`, `read:cycles`, `read:sleep`,
  `read:workout`, `read:profile`

  `offline` is the one that matters most and is easy to miss: without it WHOOP
  issues no refresh token, the connection dies an hour after it is made, and
  every open needs authorising again.

**2 · Give the server the credentials**

In Render → the service → Environment, add:

```
WHOOP_CLIENT_ID      = <from the WHOOP dashboard>
WHOOP_CLIENT_SECRET  = <from the WHOOP dashboard>
```

Optionally `WHOOP_REDIRECT_URI`, if it ever needs to differ from the address
the request arrives on.

Enter these yourself. They are credentials, and nobody should be typing them
on your behalf.

Without them nothing breaks: every WHOOP endpoint answers "not configured",
the Connect button is not drawn, and the panel keeps manual entry.

**3 · Connect**

Sleep tab → **Connect WHOOP** → sign in → you land back on the Sleep tab with
the numbers already fetched.

**A limit worth knowing about.** An unapproved WHOOP app is capped at **10
members**. That is plenty for you and is nowhere near enough to launch on. To
go past it you request approval from the WHOOP developer dashboard ("Open
Request" → "App approval"), which needs the app tested with at least one real
member, an accurate name and contact email, a privacy policy URL, and
adherence to WHOOP's brand guidelines.

**Where the tokens live.** Not with your data. The app hydrates by calling
`/api/all`, which returns every key in your account's namespace — so a refresh
token stored the ordinary way would be handed to the browser on every page
load. They go to `whoop:tok:<uid>` instead, outside the `ld_*` pattern that
`all()` enumerates. That is a structural property, not a naming convention, and
`tests/test-whoop.js` checks it.

## Connecting Apple Health

Nothing to register and nothing to pay for, but it only exists inside the iOS
app — there is no HealthKit in a browser, so the panel stays hidden there
rather than offering something that cannot work.

**1 · Rebuild the app.** `FlowHealth.swift`, the entitlement and the usage
string are all generated by the existing scripts, so a normal rebuild picks
them up.

**2 · Enable HealthKit on the App ID.** With automatic signing Xcode usually
does this itself the first time it sees the entitlement. If it complains about
a provisioning profile, enable **HealthKit** for `com.abko.theflow` in the
developer portal and let Xcode regenerate.

**3 · In the app**, Sleep tab → **Allow Health access**. iOS shows one switch
per data type; you can grant sleep and refuse heart rate.

**What Health will not tell us.** Whether you granted read permission. That is
deliberate on Apple's part — an app that could tell "denied" from "no data"
would learn something about you by being refused. So an empty read is
genuinely ambiguous, and the panel says so in both directions rather than
picking the flattering explanation.

## Reviewing this before the App Store

The privacy labels already declare Health & Fitness as data linked to you, so
nothing changes there. Two things are worth having ready for the reviewer:

- The app only ever **reads** from Health. It requests no write permission at
  all, and `NSHealthUpdateUsageDescription` is deliberately absent.
- `com.apple.developer.healthkit-access` is an empty array — this is not a
  clinical-records app, and asking for `health-records` would start a
  conversation about data we do not want.
